differential attestation · built on lean 0.1.3

Deterministic code review.

Differential attestation (DA) accepts or refuses a change from evidence about the code before and after it.

A proof that the change did only what you asked. Or the input that breaks it, with the line to fix. Same change, same verdict, every time.

Use cases

Who DA is for

DA runs both versions and compares them. What the author says about a change never affects the verdict.

01 · Agents · WITNESS

Agent-heavy repositories

DA gives the agent a witness: an input on which the two versions differ. The witness also names the source line of the first difference and a rewrite DA advises. The agent replays that input and fixes the change against it.

02 · Platform · --block witness

Platform teams

Add DA to your CI as a gate: a check that can block a pull request. Start in advisory mode: DA keeps one comment per pull request up to date on every push. Then add --block witness, and a witness blocks the pull request.

$ node langs/ts/ci/comment.mjs --repo <checkout> --base <sha> --head <sha> --post --block witness
03 · Research · judge.jsonl

Researchers

The benchmark ships with every judge verdict and both judge logs. Support for a new language merges into lean once it passes the conformance suite. That suite is the set of tests every language must pass. The command below runs it.

$ python3 -I conformance/run.py
Core features

How DA reaches a verdict

An instrument is one of DA's three ways to gather evidence. Each instrument compares the parent, the version before the change, with the candidate, the version after. Any refusal rests on that evidence. lean then gives one of five verdicts. A card below explains each one. lean reports the strongest verdict the evidence supports. That verdict claims as much as the evidence allows, and no more.

Instrument 1

Recording

A recording runs the system on a fixed set of inputs, before and after the change. You choose a scope: the part of the behaviour the change may alter. DA refuses any difference outside that scope. Inside it, the difference must equal an edit you made on a real recording.

Instrument 2

Proof

lean proves the candidate equal to the parent for every input and every world: PASS-proved. A world is every answer the outside of the function can give: files, the network, the clock. lean does this with a prover, software that checks proofs. When a component's types allow only a finite number of states, lean checks every state the component can reach: PASS-decided.

Example: in the function statement, a loop with continue became a filter and a map. The prover reports:

Equal_statement: true, 5 verified, 0 errors.

Example: the Toggle component, where an assignment is one starting setting of the component.

Toggle: PASS-decided, 8 state pairs over 2 assignment(s).
Instrument 3

Relation

A relation compares the two versions of anything that is not a function. You write its check outside the change. Examples: build and pipeline configuration, locale files, schemas and documents. With the artifact lane, the part that checks these files, DA caught 40 of 43 escaped defects.

Verdict

WITNESS

A witness is an input on which the two versions differ. lean picks that input itself. It names the source line on each side: one in the parent, one in the candidate.

Example: the ledger pair that ships with lean. In applyAll, line 15 of the candidate has <= where the parent had <. On input 17, with the argument floor at -1, the parent returns posted 1 and the candidate 0. The replay line reruns this check. The certificate below is the record of this verdict in ledger.json, the file the run writes.

Verdicts

PASS-bounded · ASK

PASS-bounded: no difference found within a stated number of inputs. A bounded pass never becomes a proof. ASK means lean names the construct it cannot read. A construct is a piece of the language's syntax.

In the output below, the verdict is PASS-bounded. The proof side, lane A, answers ASK: the code uses syntax outside what it can translate.

PASS-bounded -> usual-booking.json
# lanes.A: ASK, translate: outside the subset (unsupported-syntax)
In DA

Screen row

The screen row compares two builds of your app on the same screens: pixels, layout and the accessibility tree. lean names the app state where the two rendered screens differ.

Example: on Search, lean found a witness after a click and a timer. The two screens differ by one inserted list item:

div[2]/ul[0] insert <li key="vefqj">"vefqj"</li>

Quick start

Run lean yourself

lean, the checker inside DA, checks a change from two sides. The run side, lane B, runs both versions on inputs it picks. It needs only Node 24. The proof side, lane A, proves the two versions equal with a prover. It needs Python 3 and Dafny 4. Without Python and Dafny, lane A reports ASK.

01 · Clone

Clone lean's repository and move into it. It holds example pairs: a parent, the version before a change, and a candidate, the version after. Steps 02 and 03 use two of these pairs.

$ git clone https://github.com/NexusGPT/lean && cd lean

02 · Check one function

Give lean a parent file, a candidate file and the name of one function. lean picks which sides to run and picks the inputs. Here it finds a witness: an input on which the two versions of applyAll differ.

$ node langs/ts/check.mjs --parent langs/ts/tests/pairs/readme_ledger/parent.ts --candidate langs/ts/tests/pairs/readme_ledger/candidate.ts --unit applyAll --no-project --n 60 --seed 3 --out ledger.json
$ jq -c '.witness | {input, floor: .args[3], parent: .parent.outcome.returned.posted, candidate: .candidate.outcome.returned.posted}' ledger.json
{"input":17,"floor":-1,"parent":1,"candidate":0}

The jq command prints that witness: input 17, the floor argument -1, and the posted value each version returns.

03 · Decide a component

Check a UI component, Toggle, in every state the component can reach. lean tries every order of clicks from every prop assignment, a starting setting of the component. When it has seen every state and found no difference, the verdict is PASS-decided.

$ node langs/ts/check.mjs --parent langs/ts/tests/pairs/finite_components/parent.tsx --candidate langs/ts/tests/pairs/finite_components/candidate.tsx --unit Toggle --no-project --n 60 --out toggle.json
PASS-decided -> toggle.json # every click order from every prop assignment, decided: 8 state pairs over 2 assignment(s)

The output gives the verdict, the result file, and the state pairs and starting settings lean checked. A state pair is the parent's state and the candidate's state after the same clicks. lean compares them at every step.

Or build the Docker image, which fixes the tool versions for both sides:docker build -t lean:local .

Python is at milestone 2, the second stage of lean's Python support. It comes with five example pairs. For Python, lean's checker says what to rewrite. Its run side, lane B, uses the same result format as TypeScript.

Differential Attestation: Accepting Agent-Written Changes from Recordings, Proofs and Declared Relations, Never from the Producer's Account

It describes an acceptance gate: a check that accepts or refuses a change. The gate reads neither the change text nor any statement by its producer, the person or agent who wrote it.
